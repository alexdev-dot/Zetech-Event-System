## Authentication & Authorization

### JWT Token Authentication

- **Algorithm**: HS256
- **Secret**: Minimum 32 characters (stored in `JWT_SECRET` environment variable)
- **Expiration**: 8 hours
- **Token Structure**: Bearer token in `Authorization` header

### Role-Based Access Control (RBAC)

The application implements three user roles:

1. **user** - Regular students
2. **admin** - System administrators
3. **club_leader** - Club/organization leaders

Access control is enforced via middleware:
- `authenticateToken` - Validates JWT tokens
- `requireAdmin` - Restricts to admin role only
- `requireAdminOrLeader` - Allows both admin and club leader roles

### Token Caching

- Auth tokens are cached in memory with 30-second TTL
- Reduces database round-trips by ~99%
- Cache is invalidated on password changes

## Password Security

### Password Complexity Requirements

All passwords must meet the following criteria:
- **Minimum length**: 8 characters
- **Uppercase letters**: At least one (A-Z)
- **Lowercase letters**: At least one (a-z)
- **Numbers**: At least one (0-9)
- **Special characters**: At least one (!@#$%^&*()_+-=[]{};':"\\|,.<>/?)

### Password Hashing

- **Algorithm**: bcrypt
- **Cost factor**: 12 rounds
- **Salt**: Automatically generated by bcrypt

### Password Change Security

- Current password verification required
- New password must meet complexity requirements
- Confirmation password must match
- Auth cache invalidated after password change
- Old tokens become invalid immediately

## Rate Limiting & Brute Force Protection

### Multi-Layer Defense

**Layer 1: IP-based Rate Limiting**
- Global limiter: 2,000 requests per 15 minutes per IP
- Auth limiter: 10 login attempts per 15 minutes per IP
- Upload limiter: 10 uploads per minute
- Admin write limiter: 120 writes per minute
- Event action limiter: 20 actions per minute
- Social action limiter: 30 actions per minute

**Layer 2: Brute Force Protection**
- IP-based failure tracking
- Account-level failure tracking
- 5 failed attempts = 15 minute lockout
- Automatic cleanup of expired records every 30 minutes

### Lockout Behavior

- **IP Lockout**: Blocks all requests from the IP
- **Account Lockout**: Blocks login attempts for specific account
- Lockout duration: 15 minutes
- Lockout cleared on successful authentication

## CSRF Protection

### Implementation

- CSRF token validation middleware applied to all state-changing requests
- Tokens required in `X-CSRF-Token` header
- Exemptions:
  - GET, HEAD, OPTIONS requests
  - Authentication endpoints (`/api/auth/*`)
- Token format: 64-character hex string

### Frontend Integration

Frontend must:
1. Obtain CSRF token from server
2. Include token in `X-CSRF-Token` header for POST/PUT/PATCH/DELETE requests
3. Refresh token periodically

## File Upload Security

### Allowed File Types

- JPEG (image/jpeg, image/jpg)
- PNG (image/png)
- GIF (image/gif)
- WebP (image/webp)

### Security Measures

1. **Extension Validation**: File extensions checked against whitelist
2. **MIME Type Validation**: MIME type verified against whitelist
3. **Filename Sanitization**: Rejects filenames with path traversal characters (`..`, `/`, `\`)
4. **File Size Limits**:
   - Image uploads: 5MB maximum
   - CSV imports: 2MB maximum
5. **Single File Limit**: Only one file per upload request
6. **Unique Filenames**: Timestamp + random suffix to prevent overwrites

### Storage

- Upload directory: `backend/public/uploads/`
- Served via static file handler at `/uploads`
- No directory listing enabled

## Security Headers

### Implemented Headers

1. **HSTS (HTTP Strict Transport Security)**
   - max-age: 31536000 (1 year)
   - includeSubDomains: true
   - preload: true

2. **X-Frame-Options**
   - Action: deny
   - Prevents clickjacking attacks

3. **X-Content-Type-Options**
   - nosniff
   - Prevents MIME type sniffing

4. **X-XSS-Protection**
   - 1; mode=block
   - Enables XSS filtering

5. **Referrer-Policy**
   - strict-origin-when-cross-origin
   - Controls referrer information

6. **Content-Security-Policy**
   - See [CSP Configuration](#content-security-policy)

## Content Security Policy

### CSP Directives

```
default-src: 'self'
script-src: 'self'
style-src: 'self'
img-src: 'self' data: blob: https:
connect-src: 'self' wss: ws: https:
font-src: 'self' data: https:
object-src: 'none'
frame-src: 'none'
upgradeInsecureRequests: true
```

### Security Features

- **No inline scripts**: `'unsafe-inline'` removed
- **No eval**: `'unsafe-eval'` removed
- **No plugins**: `object-src: 'none'`
- **No frames**: `frame-src: 'none'`
- **HTTPS upgrade**: `upgradeInsecureRequests` enabled

## Data Encryption

### Data at Rest

- **Passwords**: bcrypt hashing (cost factor 12)
- **Database**: Supabase provides encryption at rest
- **Environment Variables**: Stored in `.env` file (not committed to git)

### Data in Transit

- **HTTPS**: Required in production (HSTS enforced)
- **WebSocket**: WSS (Secure WebSocket)
- **API**: All endpoints should use HTTPS in production

### Database Access

- **Connection Method**: Supabase REST API via RPC
- **Authentication**: Service role key (bypasses RLS)
- **No Direct TCP**: HTTP-based for better security

## Audit Logging

### Security Audit Logs

All security-relevant events are logged to the `security_audit_logs` table:

- **Event Types**: login attempts, password changes, account modifications
- **Actor Information**: User ID, email, role
- **Request Metadata**: IP address, user agent
- **Target Information**: Target type and ID
- **Success/Failure**: Boolean flag
- **Details**: Additional context as JSON

### Log Retention

- Logs stored in database
- Indexed for efficient querying
- Admin-only access via `/api/admin/audit-logs`

## Input Validation & Sanitization

### String Sanitization

- **Function**: `sanitizeStr(val, maxLen)`
- **Strips**: Null bytes
- **Trims**: Whitespace
- **Limits**: Maximum length (configurable)
- **Returns**: Empty string for non-string values

### Date Validation

- **Function**: `isValidDate(s)`
- **Format**: YYYY-MM-DD
- **Regex**: `^\d{4}-\d{2}-\d{2}$`

### Integer Validation

- **Function**: `isSafeInt(val)`
- **Range**: -2,147,483,647 to 2,147,483,647
- **Prevents**: Integer overflow attacks

### Request Body Limits

- JSON payload: 100KB maximum
- URL-encoded data: 100KB maximum
- File uploads: 5MB (images), 2MB (CSV)

## SQL Injection Prevention

### Parameterized Queries

All database queries use parameterized statements:

```javascript
pool.query('SELECT * FROM users WHERE id = $1', [userId])
```

### Supabase RPC

- SQL executed via Supabase's `exec_sql` RPC function
- Parameters interpolated server-side
- No raw SQL from user input

### Input Escaping

- Values escaped using `escapeValue()` function
- Handles: NULL, booleans, numbers, dates, arrays, strings
- String escaping: Backslashes and single quotes escaped

## Session Management

### JWT Tokens

- **Stateless**: No server-side session storage
- **Self-contained**: All claims in token
- **Expiration**: 8 hours
- **Refresh**: Re-login required after expiration

### Token Validation

- Signature verification using `JWT_SECRET`
- Payload validation (id, role required)
- Database verification for account status
- Cache hit reduces DB round-trips

### Session Invalidation

- Password change: All tokens invalidated
- Account deletion: Tokens rejected
- Status change: Tokens rejected

## Deployment Security

### Environment Variables

Required environment variables:

```env
# Supabase Configuration
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key

# JWT Secret (minimum 32 characters)
JWT_SECRET=your-secure-random-secret

# Client URL (for CORS)
CLIENT_URL=https://your-frontend-domain.com

# Optional: SMS Configuration
AT_API_KEY=your-africas-talking-api-key
AT_USERNAME=your-username
```

### Production Checklist

- [ ] Use strong, randomly generated `JWT_SECRET`
- [ ] Enable HTTPS with valid SSL certificate
- [ ] Set `NODE_ENV=production`

## Known Limitations

### Current Limitations

1. **In-Memory Security State**
   - Brute force protection stored in memory
   - Auth cache stored in memory
   - Does not scale across multiple instances
   - **Solution**: Implement Redis for distributed state

2. **CSRF Token Storage**
   - Basic implementation without persistent token store
   - **Solution**: Implement session-based CSRF tokens

3. **No Multi-Factor Authentication**
   - Only password-based authentication
   - **Solution**: Add TOTP for admin accounts

4. **Rate Limiting by IP**
   - Campus WiFi users share same IP
   - May affect legitimate users
   - **Solution**: Implement user-based rate limiting

5. **Token Cache Collision Risk**
   - Uses last 40 chars of JWT signature as cache key
   - **Solution**: Use full token hash or user-specific key

## Security Best Practices

### For Developers

1. **Never commit secrets** to version control
2. **Use environment variables** for sensitive data
3. **Validate all input** on both client and server
4. **Use parameterized queries** to prevent SQL injection
5. **Implement least privilege** for database access
6. **Keep dependencies updated**
7. **Review security logs regularly**
8. **Test security features** in development

### For Administrators

1. **Use strong passwords** for all accounts
2. **Enable 2FA** when available
3. **Review audit logs** regularly
4. **Monitor failed login attempts**
5. **Keep software updated**
6. **Backup data regularly**
7. **Test disaster recovery procedures**
8. **Educate users** on security best practices

### For Users

1. **Use strong, unique passwords**
2. **Don't share credentials**
3. **Report suspicious activity**
4. **Log out when done**
5. **Keep software updated**
6. **Be cautious with file uploads**
7. **Use secure networks**

## Security Incident Response

### Reporting Security Issues

If you discover a security vulnerability, please:

1. Do not publicly disclose the issue
2. Email: security@zetech.ac.ke
3. Include:
   - Description of the vulnerability
   - Steps to reproduce
   - Potential impact
   - Suggested fix (if known)

### Incident Response Plan

1. **Identification**: Monitor logs and alerts
2. **Containment**: Isolate affected systems
3. **Eradication**: Remove threat
4. **Recovery**: Restore from backups
5. **Lessons Learned**: Document and improve
